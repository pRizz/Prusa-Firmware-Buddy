# Phase 3: Artifact and Generator Parity - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning
**Mode:** Yolo

<domain>

## Phase Boundary

Phase 3 moves deterministic generators and release-artifact production from Phase 2's reference-contract placeholders into Bazel-owned actions, checks, and metadata comparisons. It should cover generated outputs, release package structure, artifact metadata, and drift gates for the current supported product surface.

This phase should not implement the Rust firmware architecture, prove runtime behavior parity, replace retained C/C++/ASM/vendor boundaries, or claim hardware/simulator parity. Those remain Phase 4 and later work. CMake/Python may remain a quarantined reference/comparison surface, but Bazel must own the normal developer-facing targets and local drift checks.

</domain>

<decisions>

## Implementation Decisions

### Release Artifact Surface

- **D-01:** Start with the master firmware package tranche: Bazel should produce or package `.bin`, `.map`, provenance metadata, `.bbf`, `.dfu`, boot/noboot variants, and resource-package outputs for representative supported products.
- **D-02:** Keep ESP, puppy, MMU, and auxiliary firmware packages visible as declared Bazel inputs/manifests in Phase 3. Do not claim auxiliary runtime parity until the later auxiliary-controller and runtime-boundary phases prove it.
- **D-03:** Signing-key handling must stay non-secret and explicit. Phase 3 may model signing metadata, test-key paths, unsigned package modes, or reference command contracts, but must not commit private key material or require private signing secrets for local verification.
- **D-04:** Full product-matrix artifact generation may be CI/manual evidence when too heavy locally. The local Phase 3 gate should still prove representative artifact targets, metadata extraction, and drift checks are wired.

### Generator Ownership

- **D-05:** Use tiered Bazel ownership. Bazel should own build-critical generated-at-build outputs such as option data/headers, resource images, resource hashes, translation compiled outputs, automata where relevant, puppy/MMU descriptors, package metadata, `.bin`, `.bbf`, `.dfu`, `.map`, and provenance outputs.
- **D-06:** Keep existing tracked generated files checked in when the repo already reviews them in source form, including `CMakePresets.json`, `doc/logging_components.md`, `include/common/visit_all_struct_fields.hpp`, `src/lang/po/Prusa-Firmware-Buddy.pot`, font/resource headers and PNG outputs, and retained web/ESP blobs.
- **D-07:** Tracked generated files must gain Bazel drift checks and explicit update targets instead of being silently regenerated by ad hoc scripts. Update targets may call existing repo generators, but check targets must fail on drift.
- **D-08:** Existing CMake/Python generator scripts may be wrapped during Phase 3 when rewriting the generator would be broader than artifact parity. The wrapper must declare inputs, outputs, tools, and source-tree write behavior clearly.

### Deterministic Drift Checks

- **D-09:** Local check-mode should guarantee deterministic invariants: declared inputs/tools, no hidden source-tree writes during check targets, normalized golden comparisons for tracked generated outputs, and normalized release metadata manifests for firmware artifacts.
- **D-10:** Use byte-for-byte comparisons only where byte identity is a valid contract, especially deterministic generated outputs and normalized package metadata. Firmware `.bin` byte parity is not a default Phase 3 claim unless the plan creates an explicit reference fixture and normalization strategy.
- **D-11:** Full firmware checksums, simulator traces, hardware smoke, and signing-sensitive release parity should be explicit CI/manual or release-candidate gates, not hidden inside routine local checks.
- **D-12:** Phase 3 verification should include a repo-owned verifier that checks required files, target queryability, representative artifact/generator actions, drift-check failure behavior where practical, and `just` facade coverage.

### Reference Comparison Boundary

- **D-13:** Compare Bazel outputs against the current reference through layered evidence: checked Phase 1 baseline artifacts, normalized semantic manifests, deterministic generated-output diffs, and quarantined CMake/Python reference commands only where needed.
- **D-14:** CMake/Python must not become the normal release authority again. Any live reference comparison target should be named as reference-only, guarded from accidental heavy execution, and excluded from the default local release path unless deliberately requested.
- **D-15:** Artifact manifests should compare product, printer, board, MCU, bootloader mode, artifact type, filenames, package structure, version/provenance fields, resource presence, and normalized hashes where stable.
- **D-16:** Diagnostic tools such as strict byte diffs or richer diff reports are acceptable for generated files and packaging diagnostics, but they should not be used to imply full Rust firmware behavior parity in Phase 3.

### the agent's Discretion

The agent may choose exact Bazel rule names, manifest schema shape, fixture layout, representative products, and helper script boundaries as long as the implementation remains deterministic, queryable through Bazel, exposed through `just`, and honest about local versus CI/manual evidence. Prefer small standard-library Python or shell helpers over broad Starlark complexity when wrapping existing generators is clearer for this phase.

## Existing Code Insights

### Reusable Assets

- `tools/bazel/reference_contract.sh` already provides guarded, named workflow dispatch. Phase 3 can replace selected reference-only branches with real Bazel-owned generator/artifact actions while preserving the guard for heavy reference comparisons.
- `tools/bazel/shell_rules.bzl` provides a local executable wrapper that Phase 3 can reuse for small shell dispatchers without adding an external ruleset.
- `tools/bazel/phase2_verify.py` is a useful model for a standard-library verifier that checks file existence, required strings, optional Bazel query, optional `just --list`, and fast local invariants.
- Phase 1 baseline artifacts already enumerate the supported product/artifact matrix and reference capture evidence classes, reducing the need to rediscover scope.

### Established Patterns

- Existing generators are mixed: some outputs are tracked and reviewed in source, some are generated under build directories, and some are manual or hook-owned. Phase 3 should classify rather than flatten them.
- Current Phase 2 Bazel targets are dry-run contracts by default; Phase 3 should make selected artifact/generator targets substantive while keeping heavy reference execution opt-in.
- Local verification should stay lightweight and honest. Heavy firmware builds, simulator flows, hardware smoke, and signing-sensitive release checks may be recorded as CI/manual evidence if they are not practical default local checks.

### Integration Points

- `just generated-check`, `just release-package`, and the Bazel labels behind them are the natural developer-facing entrypoints for Phase 3.
- Root `BUILD.bazel`, `tools/bazel/BUILD.bazel`, and product/platform labels are the natural places to expose generator and artifact targets.
- CMake/Python reference sources remain important for comparison, but Phase 3 must clearly separate reference-only checks from Bazel-owned artifact production.
