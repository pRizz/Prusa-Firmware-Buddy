## Implementation Decisions

### Release Artifact Surface

- **D-01:** Start with the master firmware package tranche: Bazel should produce or package `.bin`, `.map`, provenance metadata, `.bbf`, `.dfu`, boot/noboot variants, and resource-package outputs for representative supported products.
- **D-02:** Keep ESP, puppy, MMU, and auxiliary firmware packages visible as declared Bazel inputs/manifests in Phase 3. Do not claim auxiliary runtime parity until the later auxiliary-controller and runtime-boundary phases prove it.
- **D-03:** Signing-key handling must stay non-secret and explicit. Phase 3 may model signing metadata, test-key paths, unsigned package modes, or reference command contracts, but must not commit private key material or require private signing secrets for local verification.
- **D-04:** Full product-matrix artifact generation may be CI/manual evidence when too heavy locally. The local Phase 3 gate should still prove representative artifact targets, metadata extraction, and drift checks are wired.

### Generator Ownership

- **D-05:** Use tiered Bazel ownership. Bazel should own build-critical generated-at-build outputs such as option data/headers, resource images, resource hashes, translation compiled outputs, automata where relevant, puppy/MMU descriptors, package metadata, `.bin`, `.bbf`, `.dfu`, `.map`, and provenance outputs.
- **D-06:** Keep existing tracked generated files checked in when the repo already reviews them in source form, including `CMakePresets.json`, `doc/logging_components.md`, `include/common/visit_all_struct_fields.hpp`, `src/lang/po/Prusa-Firmware-Buddy.pot`, font/resource headers and PNG outputs, and retained web/ESP blobs.
- **D-07:** Tracked generated files must gain Bazel drift checks and explicit update targets instead of being silently regenerated by ad hoc scripts. Update targets may call existing repo generators, but check targets must fail on drift.
- **D-08:** Existing CMake/Python generator scripts may be wrapped during Phase 3 when rewriting the generator would be broader than artifact parity. The wrapper must declare inputs, outputs, tools, and source-tree write behavior clearly.

### Deterministic Drift Checks

- **D-09:** Local check-mode should guarantee deterministic invariants: declared inputs/tools, no hidden source-tree writes during check targets, normalized golden comparisons for tracked generated outputs, and normalized release metadata manifests for firmware artifacts.
- **D-10:** Use byte-for-byte comparisons only where byte identity is a valid contract, especially deterministic generated outputs and normalized package metadata. Firmware `.bin` byte parity is not a default Phase 3 claim unless the plan creates an explicit reference fixture and normalization strategy.
- **D-11:** Full firmware checksums, simulator traces, hardware smoke, and signing-sensitive release parity should be explicit CI/manual or release-candidate gates, not hidden inside routine local checks.
- **D-12:** Phase 3 verification should include a repo-owned verifier that checks required files, target queryability, representative artifact/generator actions, drift-check failure behavior where practical, and `just` facade coverage.

### Reference Comparison Boundary

- **D-13:** Compare Bazel outputs against the current reference through layered evidence: checked Phase 1 baseline artifacts, normalized semantic manifests, deterministic generated-output diffs, and quarantined CMake/Python reference commands only where needed.
- **D-14:** CMake/Python must not become the normal release authority again. Any live reference comparison target should be named as reference-only, guarded from accidental heavy execution, and excluded from the default local release path unless deliberately requested.
- **D-15:** Artifact manifests should compare product, printer, board, MCU, bootloader mode, artifact type, filenames, package structure, version/provenance fields, resource presence, and normalized hashes where stable.
- **D-16:** Diagnostic tools such as strict byte diffs or richer diff reports are acceptable for generated files and packaging diagnostics, but they should not be used to imply full Rust firmware behavior parity in Phase 3.

### the agent's Discretion

The agent may choose exact Bazel rule names, manifest schema shape, fixture layout, representative products, and helper script boundaries as long as the implementation remains deterministic, queryable through Bazel, exposed through `just`, and honest about local versus CI/manual evidence. Prefer small standard-library Python or shell helpers over broad Starlark complexity when wrapping existing generators is clearer for this phase.

## Summary

Phase 3 should convert the Phase 2 dry-run Bazel workflow labels into concrete generator, package, manifest, and drift-check targets without pretending the Rust runtime exists yet. [VERIFIED: tools/bazel/BUILD.bazel; VERIFIED: tools/bazel/reference_contract.sh; VERIFIED: .planning/phases/02-bazel-authority-and-developer-facade/02-VERIFICATION.md] The highest-leverage plan is to add a small repo-owned artifact/generator layer under `tools/bazel/`, where Bazel actions declare inputs and outputs, Python helpers normalize metadata, and `just` continues to expose the developer-facing commands. [VERIFIED: tools/bazel/shell_rules.bzl; VERIFIED: justfile; CITED: https://bazel.build/versions/9.1.0/rules/lib/builtins/actions]

The current reference surface is mixed: CMake creates firmware `.bin`, `.map`, `.bbf`, `.dfu`, resource images, option headers, and auxiliary firmware wiring; Python scripts encode BBF, DFU, LittleFS, puppy descriptors, QOI, ESP parts, translation hash tables, persistent-store hashes, and tracked generated files. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md; VERIFIED: cmake/Options.cmake]

**Primary recommendation:** Build a Bazel-owned `tools/bazel/artifacts` and `tools/bazel/generators` layer with package encoder rules, normalized JSON manifests, source-read-only drift checks, explicit source-writing update targets, and a `phase3_verify.py` verifier that proves queryability, representative actions, drift failure behavior, and `just` coverage. ## Architecture Patterns

### Recommended Project Structure

```text
tools/bazel/
  artifact_rules.bzl          # package/action rules and providers
  generator_rules.bzl         # drift/update wrappers for existing generators
  artifact_manifest.py        # stdlib manifest extraction and normalization
  generated_drift.py          # compare regenerated temp outputs to tracked files
  phase3_verify.py            # requirement verifier
  phase3_verify.sh            # shell_binary entrypoint
  reference_compare.sh        # guarded reference-only comparison dispatcher
  fixtures/
    firmware_payloads/        # deterministic tiny payloads or checked fixtures
  manifests/
    representative_products.json
```

This structure keeps Bazel glue, manifest logic, and verification local to Phase 3 workflow ownership instead of spreading package logic across root files. [VERIFIED: tools/bazel/phase2_verify.py pattern; VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

### Pattern 1: Artifact Provider and Package Encoders

**What:** Model artifact packaging as Bazel actions that consume a declared firmware payload, map/provenance metadata, resource images, and product metadata, then emit `.bin`, `.map`, `.bbf`, `.dfu`, and normalized manifest files. [VERIFIED: CMakeLists.txt; VERIFIED: cmake/Utilities.cmake; VERIFIED: utils/pack_fw.py; VERIFIED: utils/dfu.py]

**When to use:** Use this for representative Phase 3 products and later reuse the same provider when Phase 4+ replace placeholder/current payloads with real Rust firmware payloads. [VERIFIED: .planning/ROADMAP.md; VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**Example:**

```python
# Source: Bazel actions API and repo shell_rules.bzl pattern.
def _bbf_package_impl(ctx):
    bbf = ctx.actions.declare_file(ctx.label.name + ".bbf")
    manifest = ctx.actions.declare_file(ctx.label.name + ".manifest.json")

    args = ctx.actions.args()
    args.add("--version", ctx.attr.version)
    args.add("--printer-type", ctx.attr.printer_type)
    args.add("--printer-version", ctx.attr.printer_version)
    args.add("--printer-subversion", ctx.attr.printer_subversion)
    args.add("--build-number", ctx.attr.build_number)
    args.add("--no-sign")
    args.add(ctx.file.firmware_bin)

    ctx.actions.run(
        executable = ctx.executable.pack_fw,
        inputs = [ctx.file.firmware_bin] + ctx.files.resource_tlvs,
        outputs = [bbf],
        arguments = [args],
    )
```

Bazel actions declare output files through `ctx.actions.declare_file` and run declared tools through `ctx.actions.run` or `ctx.actions.run_shell`. [CITED: https://bazel.build/versions/9.1.0/rules/lib/builtins/actions]

### Pattern 2: Check/Update Split for Tracked Generated Files

**What:** Each tracked generated file group gets a read-only check target that regenerates into a temporary output directory and compares normalized output against the committed file; a separate update target may write to the source tree. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**When to use:** Use this for `CMakePresets.json`, `doc/logging_components.md`, `include/common/visit_all_struct_fields.hpp`, `src/lang/po/Prusa-Firmware-Buddy.pot`, font headers/PNGs, font indices, and retained web/ESP blobs. [VERIFIED: AGENTS.md; VERIFIED: .pre-commit-config.yaml; VERIFIED: .planning/codebase/CONCERNS.md]

**Example:**

```python
# Source: repo phase2_verify.py standard-library style.
def compare_file(expected: Path, actual: Path) -> None:
    expected_text = expected.read_text(encoding="utf-8").replace("\r\n", "\n")
    actual_text = actual.read_text(encoding="utf-8").replace("\r\n", "\n")
    if expected_text != actual_text:
        raise AssertionError(f"generated drift: {expected}")
```

### Pattern 3: Normalized Release Artifact Manifests

**What:** Emit JSON manifests that compare stable release metadata instead of defaulting to byte-for-byte firmware parity. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**When to use:** Use this for `.bbf`, `.dfu`, resource image, map/provenance, boot/noboot, auxiliary manifest, and product-profile comparisons. [VERIFIED: utils/pack_fw.py; VERIFIED: utils/dfu.py; VERIFIED: cmake/Littlefs.cmake; VERIFIED: .planning/phases/01-reference-baseline-and-safety-envelope/01-BASELINE-MATRIX.md]

**Manifest fields to require:** product, printer, board, MCU, bootloader mode, build type, artifact type, filename, package role, source label, version, build number, signing mode, resource image presence, stable hashes where valid, and evidence class such as `local-smoke`, `ci-only`, `reference-only`, or `release-candidate`. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md; VERIFIED: .planning/phases/01-reference-baseline-and-safety-envelope/01-REFERENCE-CAPTURE.md]

### Pattern 4: Representative Local Smoke, Matrix-Wide CI/Manual Evidence

**What:** The local Phase 3 gate should run a small representative set, while CI/manual release evidence covers the full product matrix. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**Recommended representative set:** Use `mini_release_noboot` for small-screen/BUDDY/no-boot/resource behavior, `coreone_release_boot` for xBuddy/bootloader/MMU/xBuddy Extension visibility, and a CI/manual `xl_release_boot` package path for Dwarf/ModularBed puppy visibility. [VERIFIED: utils/presets/presets.json; VERIFIED: ProjectOptions.cmake; VERIFIED: platforms/BUILD.bazel]

### Pattern 5: Guarded Reference Comparison

**What:** Keep reference comparisons opt-in through `BUDDY_BAZEL_EXECUTE_REFERENCE=1` or an equally explicit guard, and name targets `reference_*` when they call CMake/Python reference commands. [VERIFIED: .bazelrc; VERIFIED: tools/bazel/reference_contract.sh; VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**When to use:** Use guarded reference targets only to produce comparison manifests or CI/manual evidence, not for the default local `release-package` path. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

### Anti-Patterns to Avoid

- **Source-tree writes from check/build actions:** This violates Phase 3 read-only check expectations and makes Bazel action outputs hard to reason about. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md; CITED: https://bazel.build/versions/9.1.0/basics/hermeticity]
- **Reimplementing BBF/DFU/LittleFS formats:** Existing scripts encode the current release formats; reimplementation adds drift risk. [VERIFIED: utils/pack_fw.py; VERIFIED: utils/dfu.py; VERIFIED: utils/mklittlefs.py]
- **Using firmware `.bin` checksum parity as default proof:** Phase 3 explicitly does not claim firmware runtime byte parity unless a fixture and normalization strategy are added. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]
- **Making CMake the default release path under a Bazel label:** CMake/Python reference commands may remain guarded comparison paths, but the normal developer-facing target must be Bazel-owned and honest about payload status. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

## Common Pitfalls

### Pitfall 1: Hidden Source-Tree Writes During Checks

**What goes wrong:** A Bazel check target invokes `utils/build.py --generate-cmake-presets`, `utils/logging/generate_overview.py`, `generate_pot.sh`, or font scripts directly and updates tracked files as a side effect. [VERIFIED: .pre-commit-config.yaml; VERIFIED: utils/build.py; VERIFIED: utils/logging/generate_overview.py; VERIFIED: utils/translations_and_fonts/generate_pot.sh]

**Why it happens:** Existing generators were written for manual/pre-commit workflows and some write directly to source paths. [VERIFIED: .pre-commit-config.yaml; VERIFIED: .planning/codebase/CONCERNS.md]

**How to avoid:** Regenerate into a temporary declared output directory for checks and reserve source writes for explicitly named update targets. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**Warning signs:** `git status --short` changes after `just generated-check`, or a Bazel action has no declared output for a generated tracked file. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

### Pitfall 2: Treating Missing Bootstrap as a Generator Failure

**What goes wrong:** Packaging/resource/font actions fail because `.dependencies`, `.venv`, or Python modules such as `ecdsa`, `littlefs`, `PIL`, `numpy`, `polib`, or `qoi` are absent. [VERIFIED: requirements.txt; VERIFIED: local Python import probe]

**Why it happens:** Current repo tooling expects `utils/bootstrap.py` to create dependency/tooling state before full generator execution. [VERIFIED: utils/build.py; VERIFIED: cmake/Utilities.cmake; VERIFIED: AGENTS.md stack]

**How to avoid:** Make bootstrap a visible prerequisite and let Phase 3 verifier classify generator actions as skipped/missing-dependency instead of silently passing. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md; VERIFIED: local environment audit]

**Warning signs:** Missing `.dependencies/gcc-arm-none-eabi-13.2.1`, missing `.venv/bin/python`, or `ModuleNotFoundError` from generator imports. [VERIFIED: local environment audit]

### Pitfall 3: Overclaiming Firmware Byte Parity

**What goes wrong:** A `.bin` or `.bbf` checksum comparison is presented as runtime parity even though Rust firmware behavior is not implemented until later phases. [VERIFIED: .planning/ROADMAP.md; VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**Why it happens:** Artifact packaging and firmware behavior both produce binary files, but they prove different things. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**How to avoid:** Compare normalized artifact metadata locally and mark full checksums as CI/manual or release-candidate evidence unless an explicit fixture strategy exists. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**Warning signs:** Verifier output says "parity" without a manifest scope, fixture source, or evidence class. [VERIFIED: .planning/phases/01-reference-baseline-and-safety-envelope/01-REFERENCE-CAPTURE.md]

### Pitfall 4: Recreating CMake Option Semantics Ad Hoc

**What goes wrong:** A custom parser partially copies `ProjectOptions.cmake` feature logic and drifts from printer/board rules. [VERIFIED: ProjectOptions.cmake; VERIFIED: cmake/Options.cmake]

**Why it happens:** Option headers are generated by CMake configure functions and a large set of feature conditionals rather than one standalone generator. [VERIFIED: ProjectOptions.cmake; VERIFIED: cmake/Options.cmake]

**How to avoid:** For Phase 3, generate normalized product/option manifests from explicit Bazel platform metadata and use guarded reference CMake configure output only for comparison until Phase 4+ encode invariants in Rust/Bazel-owned types. [VERIFIED: platforms/BUILD.bazel; VERIFIED: .planning/ROADMAP.md; VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]

**Warning signs:** A Python script starts regex-parsing all of `ProjectOptions.cmake` to infer feature flags. [VERIFIED: ProjectOptions.cmake]

### Pitfall 5: Signing Secret Leakage

**What goes wrong:** A private firmware signing key path or key material is committed or required for local checks. [VERIFIED: ProjectOptions.cmake; VERIFIED: utils/build.py]

**Why it happens:** `pack_fw.py` signs by default unless `--no-sign` is passed, and CMake accepts `SIGNING_KEY` as a cache path. [VERIFIED: utils/pack_fw.py; VERIFIED: CMakeLists.txt]

**How to avoid:** Use `--no-sign`, test-key metadata, or explicitly external signing inputs for local checks, and record signing mode in manifests. [VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md; VERIFIED: utils/pack_fw.py]

**Warning signs:** Research, plan, manifest, or committed fixture contains key bytes or an unexplained real signing-key path. [VERIFIED: .planning/phases/01-reference-baseline-and-safety-envelope/01-REFERENCE-CAPTURE.md]

## Code Examples

### Manifest Extraction Boundary

```python
#!/usr/bin/env python3
from __future__ import annotations

import hashlib
import json
from pathlib import Path


def sha256_hex(path: Path) -> str:
    digest = hashlib.sha256()
    with path.open("rb") as stream:
        for chunk in iter(lambda: stream.read(1024 * 1024), b""):
            digest.update(chunk)
    return digest.hexdigest()


def write_manifest(output: Path, *, product: str, artifact: Path, kind: str) -> None:
    payload = {
        "product": product,
        "artifact_kind": kind,
        "filename": artifact.name,
        "size": artifact.stat().st_size,
        "sha256": sha256_hex(artifact),
    }
    output.write_text(json.dumps(payload, sort_keys=True, indent=2) + "\n", encoding="utf-8")
```

Use standard-library JSON and hashing for normalized manifests unless a format parser needs an existing repo helper. [VERIFIED: tools/bazel/phase2_verify.py; VERIFIED: .planning/phases/03-artifact-and-generator-parity/03-CONTEXT.md]
