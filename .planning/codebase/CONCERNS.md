## Tech Debt

**Global target coupling in firmware build:**

- Issue: The root firmware target uses a broad `BuddyHeaders` interface include surface and has TODOs for unclear header ownership and cross-target coupling.
- Files: `CMakeLists.txt`, `ProjectOptions.cmake`
- Evidence: `CMakeLists.txt:98` notes the header-target mapping needs refactoring; `CMakeLists.txt:234` notes Marlin depends on `src/common` and `src/gui`; `CMakeLists.txt:598` and `CMakeLists.txt:639` keep `error_codes_mmu` linked even when MMU should be optional.
- Impact: Adding a board, feature, or generated header can accidentally rely on global include state instead of explicit target ownership.
- Fix approach: Split `BuddyHeaders` by subsystem, make feature libraries own their include directories, and gate `error_codes_mmu` with `HAS_MMU2` once MMU build dependencies are isolated.

**Long-lived MMU compatibility stubs:**

- Issue: MMU reporting contains empty methods, hard-coded availability, and disabled sound behavior.
- Files: `src/mmu2/mmu2_reporting.cpp`, `src/mmu2/mmu2_error_converter.cpp`, `src/mmu2/mmu2_serial.cpp`
- Evidence: `src/mmu2/mmu2_reporting.cpp:75` through `src/mmu2/mmu2_reporting.cpp:89` are `@@TODO` stubs; `src/mmu2/mmu2_reporting.cpp:93` and `src/mmu2/mmu2_reporting.cpp:97` always return true; `src/mmu2/mmu2_reporting.cpp:104` returns before playing sounds; `src/mmu2/mmu2_serial.cpp:12` calls its implementation temporarily empty.
- Impact: UI feedback, availability checks, serial reporting, and maintenance flows can silently report success while behavior is missing.
- Fix approach: Replace hard-coded returns with config and runtime state, move currently unsupported behaviors behind explicit feature flags, and add unit tests around MMU availability/reporting decisions.

**Generated and manually regenerated assets are tracked without a single authoritative drift check:**

- Issue: Multiple generated artifacts are committed and regenerated by different scripts or hooks, but not all carry a visible generated marker or build-time verification.
- Files: `CMakePresets.json`, `doc/logging_components.md`, `include/common/visit_all_struct_fields.hpp`, `src/gui/res/cc/font_bold_13x22_full.hpp`, `src/guiapi/include/fnt-full-indices.ipp`, `src/lang/po/Prusa-Firmware-Buddy.pot`
- Evidence: `.pre-commit-config.yaml:21` and `.pre-commit-config.yaml:35` duplicate the `generate-log-components-overview` hook; `.pre-commit-config.yaml:27` regenerates `CMakePresets.json`; `utils/build.py:550` writes `CMakePresets.json` without a generated-file banner; `utils/translations_and_fonts/README_TRANSLATIONS.md:108` through `utils/translations_and_fonts/README_TRANSLATIONS.md:114` make font regeneration manual.
- Impact: Presets, logging docs, fonts, translations, and generated helpers can drift from their sources when hooks are skipped or generation instructions are incomplete.
- Fix approach: Add check-mode drift verification for tracked generated outputs, add generated banners where missing, and consolidate the duplicated logging hook.

**Build and translation scripts do not consistently use safe shell defaults:**

- Issue: Several repo-owned shell scripts omit `set -euo pipefail` and rely on manual `$?` checks.
- Files: `utils/translations_and_fonts/generate_all_fonts.sh`, `utils/translations_and_fonts/generate_single_font.sh`, `utils/translations_and_fonts/new_translations.sh`, `utils/translations_and_fonts/generate-translations-report.sh`
- Evidence: `utils/translations_and_fonts/generate_all_fonts.sh:1` uses `#!/bin/bash`; `utils/translations_and_fonts/generate_all_fonts.sh:14` defines a manual `fail_check`; no `set -euo pipefail` is present in the script.
- Impact: Partial translation/font generation failures can leave stale generated assets in `src/gui/res/cc/`, `src/guiapi/include/`, or `src/lang/po/`.
- Fix approach: Standardize these scripts on `#!/usr/bin/env bash`, `set -euo pipefail`, explicit dependencies, and dry-run/check modes where practical.

**Outdated manual Connect module test target:**

- Issue: A Connect module test is intentionally disabled and points at stale `src/Connect` paths that do not match current lowercase `src/connect`.
- Files: `tests/CMakeLists.txt`, `tests/module/Connect/CMakeLists.txt`, `src/connect/`
- Evidence: `tests/CMakeLists.txt:4` calls the test outdated and not compiling; `tests/module/Connect/CMakeLists.txt:9` through `tests/module/Connect/CMakeLists.txt:13` reference `src/Connect/...`.
- Impact: Historical Connect coverage cannot be re-enabled without path and API migration work.
- Fix approach: Either delete/archive the stale module test or port it to current `src/connect/` APIs and include it in a named CI/local verification target.

## Known Bugs

**Custom TLS certificate path never reads certificate bytes before parsing:**

- Symptoms: Enabling the custom Connect TLS certificate path can fail or parse uninitialized heap memory instead of the DER file content.
- Files: `src/connect/tls/tls.cpp`
- Trigger: `custom_cert` true with `/internal/connect/connect.der` present.
- Evidence: `src/connect/tls/tls.cpp:130` opens `/internal/connect/connect.der`; `src/connect/tls/tls.cpp:147` allocates `der_buffer`; `src/connect/tls/tls.cpp:152` immediately passes that buffer to `mbedtls_x509_crt_parse_der_nocopy` without a preceding `fread`.
- Workaround: Use built-in certificates until the file-read path is fixed and covered by a unit/integration test.

**Probe analysis variance mean is explicitly wrong but classifier depends on it:**

- Symptoms: Load variance and R2-derived classification are based on the last sample load divided by sample count, not the mean load.
- Files: `src/common/probe_analysis.cpp`
- Trigger: Any probe classification path using `ProbeAnalysisBase::CalculateVariance`.
- Evidence: `src/common/probe_analysis.cpp:402` states the accumulate function is wrong and that fixing it causes `classify` to fail; `src/common/probe_analysis.cpp:403` ignores the accumulator.
- Workaround: Treat current classification thresholds as coupled to the bug; fix by updating thresholds/test fixtures together.

**Home screen can freeze when flash action fails to start:**

- Symptoms: Home screen remains active with events disabled after some media/flash G-code no-ops.
- Files: `src/gui/screen_home.cpp`
- Trigger: `GUI_event_t::MEDIA` or loop-driven flash action failure around the home screen event handler.
- Evidence: `src/gui/screen_home.cpp:433` through `src/gui/screen_home.cpp:436` document the freeze and disabled-events state.
- Workaround: Avoid adding more event-disabled flows here until flash actions report start/failure through a single result path.

**Transfer partial-file progress reporting is disabled due to AsyncIO stack overflow:**

- Symptoms: Progress visualization/logging for partial file writes is compiled out.
- Files: `src/transfers/partial_file.cpp`
- Trigger: Enabling the code behind `#if 0` in `PartialFile::print_progress`.
- Evidence: `src/transfers/partial_file.cpp:368` through `src/transfers/partial_file.cpp:375` says the message overflows the AsyncIO stack.
- Workaround: Keep progress logging disabled until the message is emitted from a task with adequate stack or split into smaller telemetry.

**Block device random test can address one block past the declared range:**

- Symptoms: `select_random_block()` can return `BLOCK_COUNT` even though valid zero-based blocks are `0..BLOCK_COUNT-1`.
- Files: `tests/blockdevice/test_block_device.py`
- Trigger: `random.randint(0, BLOCK_COUNT)` returning `1900`.
- Evidence: `tests/blockdevice/test_block_device.py:5` through `tests/blockdevice/test_block_device.py:6` define `BLOCK_COUNT = 1900`; `tests/blockdevice/test_block_device.py:20` through `tests/blockdevice/test_block_device.py:21` use inclusive `randint`.
- Workaround: Use `random.randrange(BLOCK_COUNT)` before relying on this test for storage validation.

## Security Considerations

**Crash dumps include sensitive memory and optional upload uses plain socket HTTP:**

- Risk: Crash dumps can include unencrypted sensitive information and, if a server is configured, upload through `http::SocketConnectionFactory` rather than TLS.
- Files: `src/gui/screen_home.cpp`, `src/common/crash_dump/dump.cpp`, `src/common/crash_dump/crash_dump_distribute.cpp`, `src/common/crash_dump/crash_dump_distribute.hpp`
- Evidence: `src/gui/screen_home.cpp:322` through `src/gui/screen_home.cpp:325` warns users not to share dumps publicly; `src/common/crash_dump/dump.cpp:66` through `src/common/crash_dump/dump.cpp:78` dumps RAM/CCMRAM regions; `src/common/crash_dump/crash_dump_distribute.cpp:55` through `src/common/crash_dump/crash_dump_distribute.cpp:69` posts with `http::SocketConnectionFactory`; `src/common/crash_dump/crash_dump_distribute.hpp:9` leaves the server disabled by default.
- Current mitigation: Crash dump server upload is disabled by an empty default server string in `src/common/crash_dump/crash_dump_distribute.hpp`.
- Recommendations: Keep upload disabled unless TLS and consent are added; scrub known credential regions before export; document data-retention expectations for crash dump handling.

**Network secrets are stored in persistent config without visible encryption-at-rest:**

- Risk: Wi-Fi password, PrusaLink password, and Connect token are stored as `StoreItem<std::array<char,...>>` in the config store.
- Files: `src/persistent_stores/store_instances/config_store/store_definition.hpp`, `src/persistent_stores/storage_drivers/eeprom_storage.cpp`
- Evidence: `src/persistent_stores/store_instances/config_store/store_definition.hpp:203` through `src/persistent_stores/store_instances/config_store/store_definition.hpp:204` store Wi-Fi SSID/password; `src/persistent_stores/store_instances/config_store/store_definition.hpp:239` through `src/persistent_stores/store_instances/config_store/store_definition.hpp:243` store PrusaLink and Connect credentials; `src/persistent_stores/storage_drivers/eeprom_storage.cpp:15` through `src/persistent_stores/storage_drivers/eeprom_storage.cpp:17` write bytes directly through the EEPROM driver.
- Current mitigation: Not detected in the inspected store driver.
- Recommendations: If hardware allows, add encryption or credential-specific erase/export policy; at minimum document physical-access assumptions and avoid including these regions in exported diagnostics.

**TLS build enables legacy digest modules even though runtime ciphersuite is modern:**

- Risk: `MBEDTLS_SHA1_C` and `MBEDTLS_MD5_C` remain compiled into the TLS configuration, expanding the cryptographic attack surface if certificate parsing or future code paths accept legacy signatures.
- Files: `include/mbedtls/cipher_config_ece.h`, `src/connect/tls/tls.cpp`
- Evidence: `include/mbedtls/cipher_config_ece.h:32` through `include/mbedtls/cipher_config_ece.h:34` enable SHA-1 and MD5; `src/connect/tls/tls.cpp:175` through `src/connect/tls/tls.cpp:183` restrict runtime TLS to TLS 1.2 with `MBEDTLS_TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`.
- Current mitigation: Connect sets `MBEDTLS_SSL_VERIFY_REQUIRED` in `src/connect/tls/tls.cpp:178` through `src/connect/tls/tls.cpp:179` and uses a single ECDHE/ECDSA AES-GCM suite.
- Recommendations: Verify whether X.509 parsing still needs MD5/SHA1 for compatibility; disable unused legacy hashes or reject weak certificate signatures explicitly.

**RNG failure in production falls back to deterministic software LCG:**

- Risk: Security-sensitive callers that use `rand_u()` instead of `rand_u_secure()` can silently receive deterministic output after hardware RNG failure.
- Files: `src/common/random_hw.cpp`, `src/connect/tls/hardware_rng.cpp`
- Evidence: `src/common/random_hw.cpp:17` through `src/common/random_hw.cpp:30` falls back to `rand_u_sw()` in production; `src/common/random_hw.cpp:33` through `src/common/random_hw.cpp:37` implement a fixed-seed LCG and warn not to use it for anything important.
- Current mitigation: TLS entropy uses `src/connect/tls/hardware_rng.cpp` through mbedTLS hardware entropy, not the generic `rand_u()` fallback.
- Recommendations: Keep `rand_u_secure()` mandatory for cryptographic operations and rename/document `rand_u()` as non-cryptographic after fallback.

**Credential and private-key fixture files exist in vendored/test trees:**

- Risk: Secret scanners and human reviewers can confuse fixture keys with production secrets; accidental reuse would be severe.
- Files: `lib/Middlewares/Third_Party/mbedtls/tests/data_files/`, `tests/module/Connect/test-server/tls/`
- Evidence: Key and certificate fixtures are present under these test/vendor directories. Contents were not read.
- Current mitigation: These paths are vendored or test-only and are excluded from regular formatting in `.pre-commit-config.yaml`.
- Recommendations: Keep fixture keys quarantined to tests, document them as non-production, and ensure packaging/release scripts exclude test fixtures.

## Performance Bottlenecks

**LwIP packet ordering workaround intentionally limits throughput:**

- Problem: Networking sends only one packet at a time to avoid packet reordering/missing retransmit behavior.
- Files: `include/buddy/lwipopts.h`
- Cause: `include/buddy/lwipopts.h:86` through `include/buddy/lwipopts.h:104` documents a temporary workaround for packet reordering and missing second-packet send behavior.
- Improvement path: Reproduce BFW-2357 with a network integration test, isolate whether the root cause is LwIP or integration, then restore normal TCP windowing.

**TLS handshake is CPU and memory sensitive:**

- Problem: Connect TLS setup allocates from constrained pools and asks other subsystems to conserve CPU during handshake.
- Files: `src/connect/tls/tls.cpp`, `include/mbedtls/cipher_config_ece.h`
- Cause: `src/connect/tls/tls.cpp:39` through `src/connect/tls/tls.cpp:44` targets a 512B LwIP memory pool for entropy; `src/connect/tls/tls.cpp:100` through `src/connect/tls/tls.cpp:105` says the handshake is CPU intensive and can miss server timing; `include/mbedtls/cipher_config_ece.h:60` through `include/mbedtls/cipher_config_ece.h:65` limits content lengths.
- Improvement path: Add handshake latency/memory telemetry around Connect, measure worst-case with UI/network load, and consider session reuse or less allocation-sensitive context ownership.

**Connect response parsing relies on fixed whole-response buffers:**

- Problem: Connect reads responses into bounded buffers rather than streaming parse-as-data-arrives.
- Files: `src/connect/connect.cpp`, `src/connect/command.cpp`, `src/connect/render.cpp`
- Cause: `src/connect/connect.cpp:191` through `src/connect/connect.cpp:198` calls out the need for smaller buffers and larger-response handling; `src/connect/connect.cpp:207` through `src/connect/connect.cpp:214` reads bodies early to preserve connection reuse.
- Improvement path: Introduce incremental JSON/G-code parsing for Connect responses and reduce shared buffer lifetimes.

**Generated font headers dominate source size and review/build churn:**

- Problem: Tracked generated font headers are tens of thousands of lines each.
- Files: `src/gui/res/cc/font_bold_13x22_full.hpp`, `src/gui/res/cc/font_bold_11x19_full.hpp`, `src/gui/res/cc/font_regular_11x18_full.hpp`, `src/gui/res/cc/font_regular_9x16_full.hpp`
- Cause: `src/gui/res/cc/font_bold_13x22_full.hpp` has 51,748 lines; `src/gui/res/cc/font_bold_11x19_full.hpp` has 38,308 lines; `utils/translations_and_fonts/README_TRANSLATIONS.md:108` through `utils/translations_and_fonts/README_TRANSLATIONS.md:114` require manual regeneration after translation changes.
- Improvement path: Prefer binary generated assets or build-generated headers with drift checks; keep checked-in generated headers only if release tooling requires them.

## Fragile Areas

**Partial-file transfer bypasses filesystem allocation state:**

- Files: `src/transfers/partial_file.cpp`, `src/transfers/partial_file.hpp`, `src/transfers/transfer.cpp`
- Why fragile: `src/transfers/partial_file.cpp:101` through `src/transfers/partial_file.cpp:120` maps a contiguous file to sectors, closes/reopens a read-only file descriptor as a lock, and acknowledges a delete/recreate race; `src/transfers/partial_file.cpp:136` through `src/transfers/partial_file.cpp:177` writes sectors directly through USB.
- Safe modification: Preserve explicit lifetime ownership, validate media identity before writes, and add tests for unplug/replug, delete/recreate, and non-contiguous files.
- Test coverage: Unit transfer tests exist under `tests/unit/transfers/`, but hardware/media race coverage is not apparent from the inspected files.

**Transfer monitor exposes lock-order deadlocks as API rules:**

- Files: `src/transfers/monitor.hpp`, `src/transfers/monitor.cpp`
- Why fragile: `src/transfers/monitor.hpp:52` through `src/transfers/monitor.hpp:77` documents that holding `Status` while allocating/dropping `Slot`, or calling `Slot` methods while holding `Status`, deadlocks.
- Safe modification: Avoid adding nested monitor calls; prefer APIs that return snapshots instead of lock-holding objects.
- Test coverage: `tests/unit/transfers/transfer_tests.cpp` and `tests/unit/transfers/changed_path_tests.cpp` exist, but lock-order misuse is hard to prove without targeted concurrency tests.

**Connect planner/background command state machine relies heavily on asserts and shared buffers:**

- Files: `src/connect/planner.cpp`, `src/connect/background.cpp`, `src/connect/printer.hpp`
- Why fragile: `src/connect/planner.cpp:1066` through `src/connect/planner.cpp:1069` documents unresolved duplicate-command handling while a background command owns the shared buffer; `src/connect/background.cpp:50` through `src/connect/background.cpp:52` suppresses `-Wvla` for a variable-length G-code stack buffer; `src/connect/printer.hpp:260` through `src/connect/printer.hpp:263` says submitted G-code is not necessarily executed.
- Safe modification: Treat command parsing, background execution, and event reporting as one state machine; add tests for duplicate command delivery and long G-code lines before changing shared-buffer ownership.
- Test coverage: Unit tests exist under `tests/unit/connect/`, but the disabled `tests/module/Connect/` target leaves an integration gap.

**Persistent config schema is collision-sensitive and migration-heavy:**

- Files: `src/persistent_stores/store_instances/config_store/store_definition.hpp`, `src/persistent_stores/store_instances/config_store/migrations.cpp`, `utils/persistent_stores/journal_hashes_generator.py`
- Why fragile: `src/persistent_stores/store_instances/config_store/store_definition.hpp:725` through `src/persistent_stores/store_instances/config_store/store_definition.hpp:733` warns deprecated items must keep hashed IDs; `utils/persistent_stores/journal_hashes_generator.py:49` through `utils/persistent_stores/journal_hashes_generator.py:62` detects hash duplicates.
- Safe modification: Add or rename config items only with migration tests and generated hash drift verification.
- Test coverage: `tests/unit/persistent_stores/EEPROM_journal_test.cpp` exists; add explicit coverage when touching store hashes or deprecated items.

**Hardware interrupt configuration has an unimplemented STM32G0 already-enabled path:**

- Files: `src/common/Pin.cpp`
- Why fragile: `src/common/Pin.cpp:64` through `src/common/Pin.cpp:66` calls `system_core_error_handler()` for STM32G0 when configuring an already-enabled IRQ instead of checking priority like the STM32F4 path.
- Safe modification: Implement STM32G0 priority readback or make repeated IRQ configuration impossible for affected pins.
- Test coverage: Hardware-specific path likely needs target/simulator verification; host tests will not exercise HAL/NVIC behavior.

## Scaling Limits

**Aggregate struct visitor hard-caps generated arity at 255 fields:**

- Current capacity: Generated visitor handles aggregate arities below 256.
- Files: `include/common/visit_all_struct_fields.hpp`, `utils/persistent_stores/visit_all_struct_fields_generator.py`
- Limit: `include/common/visit_all_struct_fields.hpp:13` through `include/common/visit_all_struct_fields.hpp:14` asserts `arity < 256`.
- Scaling path: Regenerate with a larger bound or replace generated structured bindings with a reflection/serialization strategy that does not grow linearly in source.

**Persistent journal hash space uses 14-bit IDs:**

- Current capacity: Hash values are SHA-256-derived and masked with `0x3FFF`.
- Files: `utils/persistent_stores/journal_hashes_generator.py`, `src/persistent_stores/journal/store.hpp`
- Limit: `utils/persistent_stores/journal_hashes_generator.py:9` through `utils/persistent_stores/journal_hashes_generator.py:11` describe two MSB bytes ANDed with `0x3FFF`; collision risk grows as store items accumulate.
- Scaling path: Preserve generated duplicate detection, reserve migration space for renamed items, and consider a wider ID if config items continue to grow.

**Transfer subsystem supports a single active transfer slot:**

- Current capacity: One active transfer from Slicer/Link/Connect at a time.
- Files: `src/transfers/monitor.hpp`
- Limit: `src/transfers/monitor.hpp:28` through `src/transfers/monitor.hpp:43` describes reserving a single active transfer.
- Scaling path: Keep single-slot semantics explicit in APIs, or redesign monitor state before adding concurrent downloads/uploads.

## Dependencies at Risk

**Large vendored dependency tree is manually integrated:**

- Risk: Security and compatibility updates are difficult to audit because `lib/` contains 8,006 tracked files and `git submodule status --recursive` reports no active root submodules.
- Impact: Updates to `lib/Marlin/`, `lib/Middlewares/Third_Party/mbedtls/`, `lib/tinyusb/`, `lib/Catch2/`, `lib/TMCStepper/`, and `lib/libbgcode/` can require manual merge/reintegration.
- Migration plan: Maintain a dependency inventory with upstream commit/version for each `lib/` package, document update procedure, and run focused integration tests after vendor bumps.

**Pre-commit tooling pins old hook versions and depends on local `.dependencies`:**

- Risk: Formatting/check behavior can diverge from CI or new developer machines.
- Impact: `.pre-commit-config.yaml` pins `pre-commit-hooks` at `v2.4.0`, `cmake-format-precommit` at `v0.6.13`, and invokes `.dependencies/clang-format-16-83817c2f/clang-format`.
- Migration plan: Document bootstrap for `.dependencies`, periodically refresh hook revisions, and keep check-only CI coverage for generated files and format drift.

**Python dependencies are partially pinned and include heavyweight optional tooling:**

- Risk: Reproducibility varies because `requirements.txt` mixes exact pins and compatible ranges.
- Impact: `requirements.txt` pins `numpy==1.26.4`, `requests==2.32.3`, and `littlefs-python==0.8`, while packages such as `aiohttp~=3.8`, `easyocr~=1.7`, and `setuptools~=70.1.0` float within ranges.
- Migration plan: Use lockfile generation for CI/dev images or split runtime build requirements from optional translation/OCR/test tooling.
